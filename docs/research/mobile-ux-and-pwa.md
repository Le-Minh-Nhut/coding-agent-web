# iPhone-first UI and PWA research

## Decision

The upstream `collab-web` guest is already credible as a **responsive web client** at 390×844: it has small-screen transcript/header/composer rules, safe-area padding, touch-sized text, and keyboard viewport handling. It is not a mobile layout that needs an emergency rewrite. For Coding Agent Web, build a **thin, purpose-fit chat UI** and reuse only its browser-safe collab protocol helpers (`link.ts`, `socket.ts`, `codec.ts`, `jsonl.ts`), rather than transplanting the collab guest component stack. This keeps existing session UX focused and avoids inheriting a large tool/agent dashboard and its React/Markdown/tool-render dependencies. This is a product-fit recommendation, not a claim that upstream is broken.

## Upstream guest anatomy

`App` selects connect screen or session; the session composes `HeaderBar`, transcript, `Composer`, optional agent rail/drawer, `Banners`, and `Toasts` (`packages/collab-web/src/app.tsx:3-14,110-113,159-230`). Other components include `ConnectScreen` (`src/components/shell/ConnectScreen.tsx:13-27`), `ThemeToggle` (`src/components/shell/ThemeToggle.tsx:22-35`), `AgentsPanel` (`src/components/agents/AgentsPanel.tsx:82-88`), `AgentDrawer` (`src/components/agents/AgentDrawer.tsx:16-27`), `Transcript` (`src/components/transcript/Transcript.tsx:273-284`), `ToolCard` (`src/components/transcript/ToolCard.tsx:18-34`), and Markdown renderers (`src/components/transcript/Markdown.tsx:89-92,196-204`).

Styles are ordinary global CSS files/classes, **not CSS Modules**: `main.tsx` imports global `tokens.css` and `base.css` (`src/main.tsx:1-4`); `app.tsx` imports `shell.css` (`src/app.tsx:14`). Tokens centralize color/surface values (`src/styles/tokens.css:1-6`); shell component CSS uses those tokens (`src/components/shell/shell.css:1-3`). Responsive rules exist at max-width 900px and 640px, plus coarse-pointer sizing (`shell.css:848-925`); transcript stacks rows at 640px (`transcript.css:456-477`). Safe area is handled for header and composer (`shell.css:243-257,407-413`) and connect screen (`shell.css:700-710`). App height uses a `--viewport-height` set from `visualViewport` resize/scroll events when available (`app.tsx:80-98`; `shell.css:6-16`). Representative source lines: `shell.css:15` is `height: var(--viewport-height, 100%);`; `shell.css:412` is `padding-bottom: calc(16px + env(safe-area-inset-bottom, 0px));`; `shell.css:849` is `@media (max-width: 900px) {`; `Composer.tsx:27-29` clamps textarea height to eight rows and enables internal scrolling beyond that.

Viewport meta is `width=device-width, initial-scale=1` with `color-scheme` and theme-color metadata; it does **not** set `viewport-fit=cover` (`index.html:4-8`). It links a manifest, has an Apple touch icon, and declares standalone display/icons (`index.html:19-25`; `public/manifest.webmanifest:1-15`). No service-worker registration was found in `src/` or `index.html` (search performed). Composer is a one-to-eight-row auto-sizing textarea; Enter sends, Shift+Enter inserts newline, IME composition is guarded, and buttons expose send/stop plus host UI-request answers (`Composer.tsx:19-40,84-115,138-154,156-208,212-264`). Coarse pointers get 16px input text (`shell.css:919-925`).

**Verdict:** credible at 390×844 as-is for its guest-chat purpose; a bespoke mobile-first shell is justified for our different product, not because upstream lacks responsive or safe-area support.

## Mobile Safari and PWA constraints

- **Viewport and safe areas.** MDN says `vh` maps to the large viewport (`lvh`); `svh` is stable with browser UI expanded, while `dvh` tracks dynamic browser chrome and can resize during scrolling. Keyboard/zoom/browser chrome can shrink the visual viewport while the layout viewport stays unchanged. Use CSS viewport sizing for ordinary chrome changes and `env(safe-area-inset-*)` padding for edge controls; use `VisualViewport` resize/scroll only if real-device tests show CSS cannot keep the composer visible. [MDN viewport concepts](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/CSSOM_view/Viewport_concepts), [MDN length units](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/length), [MDN `env()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/env), [MDN VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/Visual_Viewport_API). WebKit documents `viewport-fit=cover` plus safe-area insets for edge-to-edge content; do not opt into cover without insetting controls. [WebKit](https://webkit.org/blog/7929/designing-websites-for-iphone-x/).
- **Keyboard.** The on-screen keyboard can resize the visual viewport without resizing layout viewport; fixed composer positioning based only on layout viewport can be obscured. Prefer normal flex layout and CSS first; if needed, observe top-level `visualViewport.resize` and update only the app frame/composer position, not global scroll on every event. [MDN VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/Visual_Viewport_API). Upstream already uses this pattern (`src/app.tsx:80-98`).
- **Standalone install and navigation.** Home Screen standalone mode has no browser-provided toolbar/UI; out-of-scope links can leave app context. Keep primary actions and explicit leave/back control in page; do not assume Safari chrome supplies navigation. Safari WebKit documents swipe-back as browser navigation, but exact edge-swipe behavior in installed standalone mode and our route/history setup needs an iPhone test. [Apple WWDC23 “What’s new in web apps”](https://developer.apple.com/videos/play/wwdc2023/10120/), [WebKit Safari 26 Home Screen behavior](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/), [WebKit bug 248303](https://bugs.webkit.org/show_bug.cgi?id=248303). **UNVERIFIED:** edge-swipe result in our installed app.
- **Web Push.** iOS/iPadOS 16.4+ supports Push API for web apps added to Home Screen; permission prompt must follow direct user interaction (such as tapping Subscribe). It is not a general Safari-tab push path. [WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).
- **Cookies and storage.** ITP blocks third-party cookies by default. WebKit documents removal of script-writable storage after seven days of Safari use without site interaction; its documented exception says Home Screen web apps have separate usage counters and are not expected to be removed by that Safari-use timer. Installed-app cookies/storage are separate from Safari. Do not depend on cross-site cookies or assume Safari and installed-app storage are shared. [WebKit ITP](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/), [Apple WWDC23](https://developer.apple.com/videos/play/wwdc2023/10120/).
- **WebCrypto.** AES-GCM via `crypto.subtle` needs a secure context; remote HTTP is not secure, while HTTPS and loopback (`localhost`) are secure. Deploy HTTPS/WSS; do not quietly fall back to weaker crypto. [MDN secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts), upstream WebCrypto usage (`packages/collab-web/src/lib/codec.ts:22-33`).
- **Backgrounding and WebSocket.** Treat backgrounded iPhone pages as suspendable: do not promise a live socket or continuous JS while app is backgrounded/phone locks. Apple says backgrounded native apps are briefly given time then suspended; this is not itself a web-app guarantee. A WebKit issue report records iOS 26.3 Safari closing an established socket on background and a reconnect attempt remaining stuck, including standalone mode—issue evidence, not a platform contract. Reconcile on foreground, expose reconnecting state, and test recovery; do not claim background delivery. [Apple background preparation](https://developer.apple.com/documentation/uikit/preparing-your-ui-to-run-in-the-background), [WebKit bug 308073](https://bugs.webkit.org/show_bug.cgi?id=308073), [MDN Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API).

## Rendering choices

- Use flex/grid with `100svh` as stable small-viewport baseline and `100dvh` when responsive browser-chrome resizing is desired; keep `100vh` as fallback only. Viewport units do not guarantee keyboard accommodation: use `visualViewport` only if physical Safari tests show composer is obscured. Safe-area-pad header/composer.
- Coalesce incoming stream UI updates to animation frames; update one streaming message and memoize settled rows. Do not reparse/re-render the entire transcript per token. Upstream freezes stable Markdown prefixes during streaming (`src/components/transcript/Markdown.tsx:151-204`) and memoizes settled rows (`Transcript.tsx:174-185`).
- No third-party virtual-list library. Keep a modest recent tail mounted and load earlier messages in chunks when needed: upstream mounts a 100-entry tail and prepends older windows (`Transcript.tsx:264-282,329-341`). Apply only if session history is long; ordinary short chats need no virtualization.
- Keep code readable at phone width: `pre` blocks get their own `overflow-x:auto`, never widen the transcript (`transcript.css:338-354`).
- Support system, light, and dark themes using CSS custom-property tokens and `color-scheme`; retain a manual override. Upstream already declares the scheme and applies explicit/system theme (`index.html:6,81`; `tokens.css:1-6,72-76,115-119`).

## Reuse and license

Build the UI as a thin client and reuse the specified browser-safe helpers: `src/lib/link.ts` parses links and packs/unpacks the 4-byte peer envelope (`link.ts:1-9,58-69,145-190`); `codec.ts` seals/opens AES-GCM (`codec.ts:1-6,22-48`); `socket.ts` handles WebSocket frames and reconnect (`socket.ts:1-6,33-54`); `jsonl.ts` parses incremental transcript records (`jsonl.ts:1-21`). These are upstream protocol implementation, not a replacement for validating wire compatibility.

Root upstream `LICENSE` is MIT (`/tmp/caw-poc/oh-my-pi/LICENSE:1-15`), and collab-web package also declares MIT (`packages/collab-web/package.json:3-10`). MIT permits copy, modification, and distribution if the copyright and permission notice accompany copies/substantial portions; retain the upstream notice/license with vendored code. No legal review performed.

## What we can test

Playwright device presets emulate viewport, screen size, user agent, and touch-related parameters; use WebKit at 390×844 to check overflow, transcript scrolling, composer layout, code-block scrolling, theme, and resize/reconnect logic. Simulate a shortened viewport and dropped network in browser tests. Playwright emulation is not an iPhone: it cannot establish actual iOS keyboard animation/viewport behavior, Home Screen install context, OS push permission, edge-swipe navigation, ITP eviction, or background suspension/socket recovery. Those require a physical iPhone and installed-app/Safari passes. [Playwright emulation docs](https://playwright.dev/docs/emulation). **UNVERIFIED:** no physical iPhone run was available; Playwright-specific capabilities and these platform behaviors are not validated here.
